1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя 
платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой 
осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы
выведите в мониторинг и почему?

**Ответ:**

CPU - utilization (%, по возможности per-core) и load average (1/5/15 мин). Utilization покажет, насколько ядра заняты, load average - есть ли очередь процессов, ожидающих CPU (saturation).
RAM - used/available, swap usage. Уход в своп мгновенно убьёт производительность вычислений, поэтому метрики для него я тоже выведу.
Disk space - свободное место на разделе, куда пишутся отчёты. Если отчёты копятся, диск рано или поздно забьётся, и запись начнёт падать с ошибками.
Disk inodes - отдельно от места, т.к. отчёты - это много мелких файлов, можно упереться в лимит inodes при ещё свободном месте.

2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, 
что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы 
можете ему предложить?

**Ответ:**

Я бы предложил резделить дашборды по аудиториям (Инженеры и менеджеры).
Для инженеров дашборд остается как есть. Для менеджера настроил бы следующее:

Availability (Uptime) - % времени, когда сервис был доступен клиентам.
Error rate - % неуспешных запросов (по сути производная от 5xx/4xx, но подана как "% ошибок для клиента").
Latency - сколько в среднем/в худшем случае клиент ждёт отчёт.
SLA compliance - наглядный индикатор (зелёный/жёлтый/красный) выполнения обещанного SLA за период.

4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. 
Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 
70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

**Ответ:**

Наиболее вероятные причины:

summ_2xx берётся из метрик приложения (оно логирует только то, до чего реально дошёл запрос), а summ_all_requests из balancer/proxy, который считает все входящие соединения, включая те, что до приложения не дошли (timeout, connection refused, обрыв на уровне TCP/TLS). Такие запросы это не HTTP-код, поэтому не видны ни как 4xx, ни как 5xx.
Есть коды, которые не 2xx и не 4xx/5xx — например, 3xx (редиректы) или 1xx, которые не учтены ни в числителе, ни в проверке на "ошибки".

5. Опишите основные плюсы и минусы pull и push систем мониторинга.

**Ответ:**

Плюсы Pull:

Центральный контроль над частотой опроса, не нужно трогать агенты, чтобы поменять интервал.
Отсутствие ответа на скрейп = явный и однозначный сигнал "target недоступен".
Проще безопасность: сервер сам инициирует соединения к известному списку целей, не нужно открывать входящий порт на множестве узлов.
Удобно дебажить - можно руками с помощью curl получить метрики.

Минусы Pull:

Нужна сетевая связность от сервера до каждой цели (проблема с NAT, файрволами).
Плохо подходит для короткоживущих задач (батч-джоб может завершиться раньше следующего скрейпа). Решается через pushgateway.
При очень большом флоте целей сервер должен знать обо всех них (нужен service discovery, шардирование).

Плюсы Push:

Хорошо работает из-за NAT/файрволов. Агенту нужен только исходящий доступ.
Отлично подходит для коротких задач и событийной модели.
Не нужно заранее знать топологию сети источников.

Минусы Push:

Сложнее понять, что target "упал" - отсутствие данных не отличить от "агент просто не шлёт". Нужны отдельные heartbeat-механизмы.
Центральный коллектор может быть перегружен при массовой одновременной отправке (thundering herd), нужен backpressure.
Больше поверхность атаки. Коллектор должен принимать входящие от множества источников, каждый нужно аутентифицировать.

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.
